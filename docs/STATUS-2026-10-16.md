## 3. Fixed: navigation never executed under the userscript build

Commit `267f53d`.

Symptom seen live: the agent answers "I'll show you the pricing page", the trace records a
`navigate` event, and the page never moves. Same for features and for every customer-example
request. `turn_open` stayed on `https://sbl.so/` for an entire session.

Cause, `harness.js:19` (before):

```js
if (globalThis.chrome?.runtime?.sendMessage) return chrome.runtime.sendMessage({ type: "task", ...msg }).catch(() => null);
```

Chrome exposes `chrome.runtime.sendMessage` to an **ordinary page** whenever any installed extension
declares `externally_connectable` for that origin, while leaving `chrome.runtime.id` undefined. The
script-tag build therefore took the extension path with no extension, and Chrome threw
`"must specify an Extension ID"` **synchronously** — which `.catch()` cannot absorb. The throw
escaped `save()` (`harness.js:93`) into the navigate handler:

```js
harness.js:550   await save(rid);                  // throws here
harness.js:551   location.assign(target.href);     // never reached
```

Every other guard in the bundle (`content.js:24`, `core/trace.js:15`) already tested `.id`; this one
was the outlier.

### Why it had never been seen

It is environment-dependent, not load-method-dependent. The founder's recorded Tampermonkey passes
were genuine — their profile simply had no extension exposing `chrome.runtime` to all pages. On this
machine, **Antigravity Browser Extension** (`eeijfnjmjelapkebgockoeaadonbchdd`) declares
`externally_connectable: ["<all_urls>"]`, which supplies the trigger.

That makes the defect latent in the shipped userscript build: it fires on any machine carrying such
an extension, including a prospect's laptop during a live demo.

Confirm the trigger on any page:

```javascript
({ runtime: typeof chrome?.runtime, sendMessage: typeof chrome?.runtime?.sendMessage, id: chrome?.runtime?.id })
// triggering machine: { runtime: "object", sendMessage: "function", id: undefined }
```

### The change

`.sendMessage` → `.id`, plus a `try/catch` so a synchronous throw from an invalidated extension
context falls through to the local store instead of killing the turn.

Three test stubs (`tests/fake-engine.cjs`, `tests/harness.test.cjs`, `tests/trace.test.cjs`) declared
`sendMessage` with no `runtime.id`, so the suite was passing **because of** the bug. That is why 377
tests never caught it. They model the extension context and now say so.

`tests/bg-context.test.cjs` adds four regressions, covering both paths the maintainer asked for:

| Test | Old guard | New guard |
|---|---|---|
| page context: navigate reaches `location.assign` | fail | pass |
| page context: task rides sessionStorage, extension transport untouched | fail | pass |
| extension context: task goes through the extension transport | pass | pass |
| sync throw degrades to the local store instead of killing the turn | fail | pass |

The third passes either way by design — it is the don't-break-what-works guard.

**`core/router.js` is loaded by the server, not only by the browser.** `server.mjs:11` requires it at
startup and builds the whole route prompt (RULES, knowledge, page index) server-side, so a change to
the router's RULES does **not** reach a running server by rebuilding the bundle or hard-reloading
Chrome. Restart the server. This cost a debugging cycle: the proof-honesty rule looked ineffective in
the browser while the server was still serving the RULES it had loaded ninety minutes earlier. The
tell is in the server log — the cached prefix size stays at its old value across calls.

A quick way to check what the server actually holds:

```bash
node -e 'console.log(/Proof is named, not implied/.test(require("./core/router.js").RULES))'
```

That reads the file, so it only agrees with the running server when the server was started after the
last edit. `harness.js`, `content.js` and `cursor.js` are browser-side: rebuild and reload for those.

Load `tools/sbl-local.user.js` in Tampermonkey, keep exactly one SBL injector enabled, open
`https://sbl.so`. Confirm the dock with:
